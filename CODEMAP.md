# CODEMAP.md

A short structural map of the actual codebase — not what the app is (`spec.md`), not the build order (`PLAN.md`), not what happened (`DEVLOG.md`): where things physically live. Updated on real structural change (a new major component, a folder reorganization, a new shared module), not every session — same discipline as `spec.md`, not a diary.

Added on external review, Sept 2026: without this, every session re-derives the codebase's shape by reading around it, and across many sessions that's how two components quietly end up doing the same job.

---

## Top-level structure

React + Vite app, plain JavaScript (no TypeScript — not asked for, and Markus never reads the code directly). Built with `npm run build` into `dist/` (gitignored), deployed to GitHub Pages by `.github/workflows/deploy.yml` on every push to `main`.

- `index.html` — Vite entry HTML; loads `src/main.jsx`.
- `vite.config.js` — React plugin, Tailwind v4 (`@tailwindcss/vite`), and `vite-plugin-pwa` (see below). `base: '/Geld/'` because the app is served from a GitHub Pages project site, not its own domain.
- `src/main.jsx` — app entry point; registers the service worker (`virtual:pwa-register`) and mounts `<App />`.
- `src/App.jsx` — the app shell: sign-in/sign-out, the auth-gate screens, and (**built Sept 2026, PLAN.md Phase 2's first deliverable**) the real nav shell from spec.md §1b.2, via `NavShell.jsx`. Owns `view` (which nav item is active — one of `NavShell`'s own item ids, not a URL — §1b.1's "one static page, no separate routes") and the global `year`/`years` (§1b.2a — see `NavShell.jsx` below for why `years` flows *up* from `Konten`, not down). `Planung` (real, mounted once and hidden like Konten/Verlauf — see its own entry below), `ImportExportScreen` (real — the former separate "Datenimport"/"Sicherung" header toggles, now one nav destination with two tabs) and `PlaceholderScreen` (every other item: Dashboard, Quickview, Fortschritt, Monatsabschluss, Außenstände, Settings — none built yet) are still conditionally rendered on `view`. **`Konten` and `Verlauf` are not, anymore (Sept 2026, corrected — see below) — both render unconditionally, always, each wrapped in its own `<div>` toggling Tailwind's `hidden` by `view`, never actually unmounted.** **Owns each screen's own remembered cursor position too (Sept 2026, Markus: "save the cursor position both in konten and verlauf, and place the cursor there again upon switching")** — `kontenFocus`/`verlaufFocus` state, passed down as `initialFocus`/`onFocusChange` props to each screen, plus a new `active={view === 'konten'}`/`active={view === 'verlauf'}` prop (see below). **Corrected the same session, real usage a round later (Markus: "it seems like the tables are reconstructed every time i switch between screens — is this really necessary?")** — it wasn't: the original design conditionally rendered `{view === 'konten' && <Konten .../>}`, fully *unmounting* the inactive screen on every switch and destroying all of its local state/refs, which is exactly why cursor position needed the elaborate `initialFocus`/`onFocusChange` cross-mount plumbing in the first place — and why that plumbing still had real gaps (a fresh mount every time is a lot of surface area for something to go stale). Fixed at the root: both screens mount once, permanently, and are only ever hidden via CSS from then on — see each screen's own section below (`src/Konten.jsx`, `src/Verlauf.jsx`) for what changed there as a result (the new `active` prop, real DOM focus needing explicit re-establishment on every switch since it doesn't survive `display: none` on its own). The wrapping `<div>` around each screen carries `flex flex-1 flex-col min-h-0` while visible (`hidden` while not) — needed because `NavShell.jsx`'s own `<main>` is a flex column and Verlauf's internal layout depends on being a *direct* flex child of one; a plain wrapper div would have silently broken that.
- `src/NavShell.jsx` — the shell chrome itself: header (burger + "Geld" + active screen title + the year selector + the day/night toggle), a tablet sidebar (all `ALL_ITEMS`, hidden below the `md` breakpoint), and a phone bottom nav (`PRIMARY_ITEMS` + "More", hidden at `md` and above) — one CSS breakpoint switching layout, never two code paths (spec.md §1's own requirement). `PRIMARY_ITEMS`/`MORE_ITEMS` (exported) are the *phone* layout (bottom bar / More sheet); `ALL_ITEMS` (exported, built from them by an explicit `NAV_ORDER`, Quickview before Planung since Oct 2026) is the sidebar and Ctrl+1…0 order — together the single source of truth for the item list/labels/ids — `App.jsx`'s own routing switch reads the same ids. **Sidebar is collapsible** (Markus's own addition on top of spec.md §1b.2, written into the spec itself when this was built) — a burger button top-left, next to "Geld", toggles it; collapsed state is a plain `localStorage` boolean (`geld-sidebar-collapsed`, wrapped in try/catch — a per-device UI convenience, never synced app data), and collapsing hides the sidebar *entirely* (not an icon-only rail) so the content area actually gets the full width back. Phone's "More" button opens a bottom sheet listing `MORE_ITEMS`, dismissible by backdrop click or Escape — same destinations the tablet sidebar shows inline, per spec.md §1b.2's "layout difference, not a capability difference." **Sign-out gets a real confirmation modal (Sept 2026, Markus's explicit call for this one action specifically)** — not the two-click arm/confirm pattern Konten's own delete uses; a plain centered modal, dismissible by backdrop click or Escape, same conventions as every other modal in the app. **Ctrl/Cmd+1 through +9, then +0 for the 10th, jump straight to that `ALL_ITEMS` entry** (Sept 2026, Markus) — flagged as a real, near-certain risk rather than assumed to work: Ctrl+1–8 (Ctrl+9 = last tab) are Chrome/Firefox/Edge's own reserved "switch to browser tab N" in an ordinary tab, the same browser-chrome-level reservation class already hit for Ctrl+T/H elsewhere in this app; may work in an installed PWA's standalone window (no tab strip to reserve it for), genuinely unconfirmed without testing on Markus's own devices. Its own `<main>`/sidebar `<nav>` scroll containers now carry `overscroll-none` directly (Markus: pull-to-refresh was still reachable on Verlauf) — the body-level fix (spec.md §1) predates this shell's own nested scroll containers, and overscroll-behavior doesn't automatically extend to a descendant scrolling element just because an ancestor has it.
  - **Day/night toggle + account info relocated (Sept 2026, Markus, spec.md §1b.5/§1b.2 corrections).** A sun/moon button now sits at the very right edge of the header, calling `src/lib/theme.js`'s `toggleTheme()`; a local `isDark` state mirrors the effective theme (recomputed on both a system `prefers-color-scheme` change and `theme.js`'s own `'geld-theme-change'` event, the same dual-source pattern `gridColorScheme.js` uses for the grid). The e-mail text + "Abmelden" button that used to sit in the header's own right-aligned group moved out entirely, into a new shared `UserBadge` component (profile picture — `photoURL`, a new prop threaded down from `App.jsx`'s `user.photoURL` — or a plain lettered circle if the account has none, plus Abmelden; e-mail survives only as the button's `title` tooltip and the "(zwischengespeichert)" suffix). `UserBadge` renders twice, never duplicated: pinned to the bottom of the tablet sidebar's own `<nav>` (which is now a two-part flex column — a scrollable nav-items `<div>` above, `UserBadge` fixed below), and again as the footer of phone's "More" sheet, which has no sidebar of its own to hold it.
- `src/PlaceholderScreen.jsx` — the "kommt noch" stand-in every not-yet-built nav destination renders (resolved Sept 2026, Markus: every item gets a real nav entry from the start rather than being added incrementally per phase).
- `src/ImportExportScreen.jsx` — wraps `ImportScreen`/`BackupScreen` as two tabs under spec.md §1b.2's one "Import/Export" nav item; each screen itself is unchanged, just no longer reachable via its own independent header toggle.
- `src/firebase.js` — Firebase `app`/`auth`/`db` initialization. Firestore is initialized with `persistentLocalCache` + `persistentMultipleTabManager` (spec.md §1a's "offline cache is the real data store, not a bolt-on").
- `src/firebaseConfig.js` — the public Firebase project config object (not secret, safe to commit — see the comment in the file).
- `src/lib/authReady.js` — `waitForInitialAuthState()`, the bounded (4s) timeout around Firebase Auth (a timeout with no user keeps "Lädt…" for up to `AUTH_GIVE_UP_MS` = 30 s before the sign-in button shows, Oct 2026)'s own init calls (spec.md §1a's cold-start-stall mitigation). Any future code that needs "is there a signed-in user yet" at startup should use this rather than reading `auth.currentUser` directly or assuming `onAuthStateChanged` fires promptly.
- `src/lib/theme.js` — **new module (Sept 2026, PLAN.md Phase 2 continuation, Markus: the day/night toggle from spec.md §1b.5's corrected placement).** `readTheme()`/`effectiveDark()`/`toggleTheme()`/`applyTheme()`/`initTheme()` — a manual light/dark override layered on top of `index.css`'s `prefers-color-scheme` default, persisted per device (`geld-theme` in `localStorage`, same try/catch-wrapped pattern as `NavShell.jsx`'s `sidebarCollapsed`). `applyTheme()` sets `data-theme` on `<html>` (what `index.css`'s selectors key off) and fires a plain `window` `'geld-theme-change'` event so `src/lib/gridColorScheme.js` (a separate module, AG-Grid-specific) can react to the same override without importing this file directly. `initTheme()` runs once in `main.jsx`, before React mounts, so a previously-chosen override applies immediately rather than flashing the system default first.
- `src/sw.js` — hand-written service worker source, built via `vite-plugin-pwa`'s `injectManifest` strategy (**not** `generateSW`, which is the default and does *not* give network-first navigation — a real footgun already hit once during Phase 0: the option is `strategies` (plural), and a `strategy` typo silently falls back to `generateSW` with no error). Implements: precache-and-route from the real build manifest, and a `NavigationRoute` wrapped in `NetworkFirst` (2.5s timeout, `app-shell` cache) so navigation never serves a stale cached shell while online (spec.md §1a).
- `src/index.css` — Tailwind import, the semantic color tokens from spec.md §1b.4 (as CSS custom properties, light + `prefers-color-scheme: dark`), self-hosted Inter/JetBrains Mono via `@fontsource/*` (not a Google Fonts CDN link — offline-first means no runtime dependency on a third-party host for something as basic as page text), and the `overscroll-behavior: none` / `touch-action: pan-y` fix from spec.md §1. **Manual dark-mode override (Sept 2026, spec.md §1b.5 correction) layers on top of the media query rather than replacing it**: the dark-values block's selector gained a `:not([data-theme])` guard, and a new `:root[data-theme='dark']` block (duplicating the same dark values, higher specificity than the plain `:root` the media query falls back to) wins regardless of system preference once `src/lib/theme.js` sets that attribute. No matching `[data-theme='light']` block exists or is needed — the guard alone already lets base `:root`'s light values stand whenever any override is set.
- `public/icons/` — placeholder PWA icons (flat-color circle mark, programmatically generated, not a real design) — swap these out whenever real icon design happens; nothing depends on their current appearance.
- `firebase.json` / `.firebaserc` / `firestore.rules` / `firestore.indexes.json` — Firestore-only Firebase config (no `hosting` key — GitHub Pages serves the app, not Firebase Hosting, per spec.md §1b.1). `firestore.rules` is live with the real single-admin-UID rule (§1a/§1b.1) — Markus's actual Google account UID, not a placeholder — confirmed working via real signed-in usage throughout Phase 1a/1b (the 2026-09-22 import, and all of Konten's real editing since).

## Screen-to-component map

- `src/Konten.jsx` — the main ledger grid (PLAN.md Phase 1a). Loads `accounts`/`categories`/`transactions` live via `onSnapshot` (all-time, not year-scoped — `balance()` needs the full history, §2.1/§2.3/§2.8), computes a year list from the loaded transactions' own dates, and renders a pinned per-`reportingGroup` balance panel (`REPORTING_GROUPS`: Barkonten, Bargeld, Sparkonten, Geldanlage, Außenstände, in that fixed order — Bargeld added Sept 2026, Markus: the five `physical-cash` accounts split into their own panel, purely a display reorganization, via `jahresende()`) above an AG Grid (`ag-grid-community`/`ag-grid-react`, Theming API — `themeQuartz`, Community-tier `AllCommunityModule`) listing the selected year's transactions. Panel grid widened `lg:grid-cols-4` → `lg:grid-cols-5` to fit the new group in one row. **Confirmed against the real 2025 import: every account's Jahresende matches the Gsheet's own closing balance** — Phase 1a's actual testable deliverable (PLAN.md).
  - **The grid follows system dark mode now, like the rest of the app** — `src/lib/gridColorScheme.js`'s `syncAgGridColorScheme()` (called once, at module load). `themeQuartz` ships light/dark params out of the box (its `colorSchemeVariable` part), but they're gated behind a `data-ag-theme-mode` attribute on `<html>`/`<body>` that nothing was ever setting, so the grid always rendered in its light default regardless of the app shell correctly following `prefers-color-scheme` via CSS (Markus: illegible in dark mode). Verified visually with a standalone Playwright harness (not just read from source) before shipping — AG Grid's own dark palette, not tied to this app's own CSS tokens, so it won't match exactly, but reads correctly and legibly. Reusable as-is for a future AG Grid screen (Verlauf, §1b.3) — idempotent if called again. **Extended (Sept 2026) to also track the header's manual day/night override** — its own `effectiveDark()` helper reads `<html data-theme>` directly (not an import of `src/lib/theme.js`, to avoid coupling a grid-specific module to the app-wide one) and re-derives on both a system `prefers-color-scheme` change and `theme.js`'s `'geld-theme-change'` event, so toggling the header button flips the grid's own palette too, not just the app shell's CSS tokens.
  - **Column order matches spec.md §3a exactly:** Datum → Konto → Empfänger → Betrag → Kategorie → Unterkategorie → Details → Tags (plus an unlabeled, pinned-right delete column, not part of the spec'd order). Konto is one merged column showing the primary account with an arrow to the second one for a transfer (not Konto1/Konto2 — see spec.md §3a's note on why). Kategorie (the parent group) is derived from Unterkategorie's `parentCategoryId`, never stored separately. `signedFor(tx, accountId)` — the same magnitude-by-position rule `balance()` uses — powers the Betrag column, the Konto arrow's direction, and the account filter below.
  - **Account filter** (a `<select>` grouped by reportingGroup via `<optgroup>`, plus clicking an account in the pinned panel): matches every transaction where the chosen account is either side, and re-displays Konto/Betrag from that account's own perspective (the other account, and the amount signed relative to it). The pinned panel's own account buttons have their own roving keyboard navigation (below), richer than the plain `<select>`.
  - **Manual entry is fully built**: "+ Neue Buchung" creates a blank row below the selected one (pre-filled with the active account filter, if any) and cell-focuses its Datum cell without starting to edit it; every column is editable in place via one `setDoc` full-overwrite per commit (`persistTx`). Deleting is a pinned trashcan (or the keyboard Delete key) with a two-click arm/confirm — the armed row tints pale red (`--color-alert-tint`) and Escape discharges it. This is a real hard `deleteDoc`, not spec.md §2.9a's planned soft-delete-with-recovery-window (Phase 1b) — Firestore's PITR (7-day window, since Phase 0) is the actual safety net until then.
  - **Split transactions (§3a's auto-remainder mechanism, Phase 1b) are built.** AG Grid Community has no master/detail row support (that's Enterprise-only) — `displayRows` (a `useMemo` flat-mapping `rows`) is the Community-tier equivalent: an expanded split transaction's `lines[]` get interleaved right after their parent as synthetic rows (`{ id, __isLine: true, __parent, __lineIndex }`, `__parent` a live reference into `rows`), and every column def branches on `p.data.__isLine` to render/edit differently for a line row vs. its parent. A pinned-left "split" column (`colId: 'split'`) handles expand/add: ✚ on an unsplit parent starts the first split and auto-expands; a chevron toggles `expandedIds` once split (`>1` lines); the *last* line (the live remainder) also gets ✚ to split further. Appending a blank line is the same operation whether it's the first split or splitting an existing remainder further — no special-casing needed, since the previously-last line simply becomes directly editable and the newly-appended one becomes the new remainder. **Removing a line goes through the trashcan column instead** (Markus) — it arms/confirms/red-tints exactly like deleting a whole transaction (`handleDeleteClick` now takes the row itself and branches: `removeLine` for a line row, `softDeleteTx` for a parent — see soft-delete below, PLAN.md Phase 1b), not a separate instant-remove affordance; `confirmDeleteId` doesn't care whether the id it holds belongs to a parent or a line row.
  - **Soft-delete with a recovery window (spec.md §2.9a's layer 4, PLAN.md Phase 1b — built Sept 2026).** Deleting a whole transaction (the trashcan's confirm click, or `Konten.jsx`'s Delete-key handler) now calls `softDeleteTx(tx)` — `persistTx({ ...tx, deletedAt: Date.now() })` — instead of a real `deleteDoc`. A line's own removal (`removeLine`) is unaffected — that's still an immediate, real edit to the parent's `lines[]`, never soft-deleted itself; only a whole-transaction delete goes through this layer.
    - **`activeTransactions`** (`useMemo(() => transactions.filter((t) => !t.deletedAt), [transactions])`) is what every aggregation actually reads now — `jahresende`/`tagJahresende`/`tagFilterTotal` calls in the pinned panel and the toolbar's "Angezeigt:" readout, plus `usedTagValues`/`recentTagValues`'s usage-derived tag suggestions. `transactions` itself (raw, including soft-deleted rows) is still what `rows` (the grid's own row source) and `years` (the year-picker) read directly — a soft-deleted row needs to stay reachable there for recovery, and a year shouldn't vanish from the picker just because everything in it happens to be currently deleted.
    - **`showDeleted`** state, off by default, behind a "Kürzlich gelöscht" checkbox in the toolbar (spec.md's own "existing filter bar" placement) — `rows`' own filter chain gets one more clause, `showDeleted || !t.deletedAt`, so a soft-deleted row reappears in the grid (interleaved by date, same as any other row) only while the toggle is on, never changing what `activeTransactions` (and therefore every balance) already excludes regardless of the toggle. Its own explanatory `title` tooltip (added, then removed the same round — Markus) is gone; the checkbox is plain text now.
    - **Manual "empty the trash" (Sept 2026, Markus: "i need a function to permanently delete all 'kürzlich gelöscht' rows... in case i have to delete a large number of rows for any reason")** — a 🗑 button appears right next to the checkbox label, only while it's checked, opening a confirmation modal (`confirmPurgeOpen` state; a plain `position: fixed` overlay, not a portal — renders correctly regardless of nesting depth) rather than acting on click alone. Confirming calls `purgeAllDeleted()`, which `deleteDoc`s *every* currently soft-deleted transaction directly — not scoped to the selected year (a real "clean up a large number of rows" could span years) — distinct from the automatic ~week-later purge below, which only ever catches up on its own schedule rather than on demand. Escape also closes the modal (its own small effect, same pattern as the armed-delete Escape discharge above).

- **`budgetBreakdownLineMonths`/`breakdownGroupMonthActual`** — same file, same tests (Sept 2026, breakdown-line rows). `budgetBreakdownLineMonths` reads one specific breakdown line's own 12 months (unlike `budgetTopLineMonths`, which sums *every* breakdown row into the top-line total) — powers each breakdown row's own display/edit in Verlauf. `breakdownGroupMonthActual` is the parent-tag "(automatisch)" rollup header's own actual once a month closes — a narrower `categoryMonthActual`: only lines that are *both* in the category *and* carry the parent tag or one of its children count, not every transaction in the category (that's what the plain Prog row already shows).
- **`breakdownGroupAllocationMonthActual(allocationTagId, tagIds, year, month, transactions, tags)`** — same file, same tests, 2 new cases (Sept 2026, real bug fix — see `Verlauf.jsx`'s own "third follow-up round" section above for the full writeup). The allocation-tag-side equivalent of `breakdownGroupMonthActual` above, which only ever covered the category side — a Rollup row for an allocation-tag-targeted breakdown group (e.g. Sparen Familie → Fonds/Fonds-A) had no actuals function of its own and silently fell back to 0 for every closed month. Mirrors `allocationMonthActual`'s own position-based sign convention (against the tag's `reconciliationTargetAccountIds`), filtered to only the lines carrying one of `tagIds` — the same "filtered by tag set, not by category" shape `breakdownGroupMonthActual` already uses on the category side.
- **`progMonths(targetKey, targetId, plan1Months, closedMonths, year, transactions, tags)`** — same file, same tests (Sept 2026, moved out of `Verlauf.jsx`'s inline function when Planung needed it). Prog per month: closed month → real actual, open month → Plan1. Verlauf and Planung's Prog lens both call it, so they can't disagree.
- **`regularShare(referenceMonths)` / `splitYear(yearCents, share)`** — same file, same tests (Sept 2026, Planung). spec.md §2.8's median-based regular/lump split: share = median × 12 / reference total (null or zero total → 0, i.e. 100 % einmalig; over 100 % not clamped); `splitYear` applies it to the displayed figure, einmal being the exact remainder.
- **`planungSummary({ einnahmen, fixkosten, jahresanfang, puffer, ausgaben, ruecklagen })`** — same file, same tests (Sept 2026 — PLAN.md Phase 2's promised "§3c Budget formula" test). Budget = Einnahmen + Fixkosten + (Jahresanfang − Puffer); Ausgaben vs. Budget = Budget + Ausgaben + Rücklagen. Tested against spec.md §3c's already-published aggregate figures (104.344 / 7.344 / 64.682), which is the one exception to the synthetic-fixtures rule, since those totals are already public in the spec.
- **`centsToEuro(cents)`** — `src/lib/format.js`, no dedicated test file (a one-line `toLocaleString` wrapper, exercised indirectly by every screen that renders a currency figure). Pulled out of `Konten.jsx` this round once `Verlauf.jsx` needed the exact same formatting — was a private, unexported function there before.
- **`centsToWholeEuro(cents)`** — same file (Sept 2026, Markus: "round all values to full euros"). `Math.round(cents / 100).toLocaleString('de-DE')`, no decimals — a display-only rounding for Verlauf specifically; never used anywhere that writes back to Firestore, where cents stay exact (§2.1).
- **`parseWholeEuroInput(s)`** — same file (moved out of `Verlauf.jsx`, Sept 2026, when Planung's Puffer input needed it). Typed whole-euro text → cents; strips German thousands dots; empty → 0, unparseable → null.
- **Display order constants** — `src/lib/categoryOrder.js` (Sept 2026, moved out of `Verlauf.jsx`): `GROUP_ORDER`, `SUBCAT_ORDER`, `isKnownSubcat()` (hides Erstattungen and any category not in the list), `ALLOCATION_TAG_ORDER`. Also `UNPLANNED_ALLOCATION_TAGS` / `isBudgetPlannedTag()` (Oct 2026): allocation tags that are only labels and get no row in Verlauf or Planung — currently `tagesgeld`. A tag missing from `ALLOCATION_TAG_ORDER` would sort to the *top* (indexOf −1), so it has to be excluded explicitly, not just left out of the list. Verlauf and Planung both import these, so their row order is identical.
- **`visibleSum(rows, anchored)`** — `src/lib/visibleSum.js`, tested in `src/lib/visibleSum.test.js` (Sept 2026). Konten's "Angezeigt" total over the grid's visible rows: skips lines whose booking row is visible, skips soft-deleted rows, and returns null when (unanchored) the same account pair appears in both transfer directions. `Konten.jsx` feeds it from `onModelUpdated` via `recomputeVisibleSum()` (`forEachNodeAfterFilterAndSort`, Betrag as displayed).
- **`registerScreenCursor(screenId, fn)` / `focusScreenCursor(screenId)`** — `src/lib/screenCursor.js`, no unit test (DOM focus; verified end to end in a browser against the real `App`). "Tab places the cursor" (Oct 2026): `Konten`, `Verlauf` and `Planung` each register a `placeCursorFromTab` function (remembered cell, else the first cell in view; returns whether it placed one). `App.jsx` has one capture-phase `keydown` listener that, on a plain Tab with focus on the page itself (`document.body`) and no `.fixed.inset-0` dialog open, calls the active screen's function and cancels the Tab. `NavShell.navigate()` blurs the clicked nav button so the next Tab counts as "nothing focused".
- **`reloadApp()`** — `src/lib/reloadApp.js`, no unit test (it is service-worker lifecycle; verified against a real preview build in a browser instead). Asks for a SW update, waits for the new worker to activate, then reloads. Called by the ⟳ button in `NavShell.jsx`'s header.

## Known duplication or drift to watch

- **Planung adds a third copy of the same `onSnapshot` subscriptions (Sept 2026)** — `Planung.jsx` subscribes to the same collections Konten and Verlauf already do (plus `accounts`/`categoryYearSettings`). Same accepted trade-off as the Verlauf bullet below. If a fourth screen (Dashboard) needs them too, that's the point to lift the subscriptions into one shared data provider instead of copying them again.
- **Soft-delete filtering is done separately per screen** — Konten via `activeTransactions`, Verlauf and Planung by filtering `deletedAt` at load. Same rule written three times; a shared loader would fix it (same as the bullet above).
- **Resolved Sept 2026 (was flagged here as pending):** the year selector now lives in `NavShell.jsx`'s own header, controlled from `App.jsx` — `Konten.jsx` no longer owns `year` as local state. `Konten` still is the *only* screen that computes `years` (which years actually have data) and reports it up via `onYearsChange`; `Verlauf.jsx` doesn't need to duplicate that specific computation since it doesn't drive the selector's own options, so this particular worry didn't reproduce.
- **New, real duplication instead (Sept 2026, `Verlauf.jsx`'s own build):** `Verlauf.jsx` loads `categories`/`tags`/`transactions` via its own independent `onSnapshot` calls, byte-for-byte the same subscriptions `Konten.jsx` already has running whenever both screens are mounted-but-hidden simultaneously (they're not — `App.jsx` only renders whichever `view` is active — so today this is double Firestore listener setup/teardown on navigation, not double-held data at once, but still the same collections read twice independently rather than once and shared). Accepted deliberately for this first pass rather than building a shared data-loading layer speculatively; worth revisiting once Planung (a third screen needing the same `categories`/`tags`/`transactions`) makes the pattern three-deep instead of two.
- **Another one, same shape, deliberate (Sept 2026, breakdown-line creation; narrowed the same round `AddBreakdownModal` replaced the colon-syntax prompt):** `Verlauf.jsx`'s `createPlainGroupingTag()` is a scoped-down duplicate of `Konten.jsx`'s own `createPlainTag()` — same slugify-with-collision-suffix logic, just without Konten's own create-type picker wiring. (`createBreakdownTag()`, the colon-parsing wrapper this bullet used to also flag, is gone — `handleAddBreakdownSubmit()` resolves an existing parent by exact name match directly, the same "reuse by exact name" rule `Konten.jsx`'s own `createTag()` applies, just inlined rather than sharing that function.) Not extracted into a shared module: the two call sites want slightly different things, and each function is short enough that the indirection of a shared abstraction across two screens isn't obviously worth it yet. Flagged here per this file's own standing discipline, not silently accepted — revisit if a third screen needs the same "create/reuse a grouping tag by name" logic, or if the two copies are ever caught drifting apart.
- **Ctrl+Tab is now the same shortcut in both screens (Sept 2026)** — `Konten.jsx`'s `onCellKeyDown` gained a Ctrl+Tab branch calling its existing `toggleExpanded(tx.id)` (the same function its own chevron button already called, `expandedIds`, unchanged), a no-op on a transaction that isn't actually split. No new state or duplicated logic — just a second way to trigger the same existing toggle, matching `Verlauf.jsx`'s own Ctrl+Tab for breakdown blocks (above).
