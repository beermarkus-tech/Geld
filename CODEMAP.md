# CODEMAP.md

A short structural map of the actual codebase — not what the app is (`spec.md`), not the build order (`PLAN.md`), not what happened (`DEVLOG.md`): where things physically live. Updated on real structural change (a new major component, a folder reorganization, a new shared module), not every session — same discipline as `spec.md`, not a diary.

Added on external review, Sept 2026: without this, every session re-derives the codebase's shape by reading around it, and across many sessions that's how two components quietly end up doing the same job.

---

## Top-level structure

React + Vite app, plain JavaScript (no TypeScript — not asked for, and Markus never reads the code directly). Built with `npm run build` into `dist/` (gitignored), deployed to GitHub Pages by `.github/workflows/deploy.yml` on every push to `main`.

- `index.html` — Vite entry HTML; loads `src/main.jsx`.
- `vite.config.js` — React plugin, Tailwind v4 (`@tailwindcss/vite`), and `vite-plugin-pwa` (see below). `base: '/Geld/'` because the app is served from a GitHub Pages project site, not its own domain.
- `src/main.jsx` — app entry point; registers the service worker (`virtual:pwa-register`) and mounts `<App />`.
- `src/App.jsx` — the app shell: sign-in/sign-out, the auth-gate screens, and the header (year selector lives inside `Konten.jsx` for now, not here — §1b.2a's "single shared header" isn't built yet). Renders `Konten` as the default/only real screen; `ImportScreen` is reachable via a "Datenimport" toggle button in the header, not a real nav shell — see PLAN.md Phase 3's note on why that's scheduled for later, once a third real screen (Verlauf) exists to make a toggle insufficient.
- `src/firebase.js` — Firebase `app`/`auth`/`db` initialization. Firestore is initialized with `persistentLocalCache` + `persistentMultipleTabManager` (spec.md §1a's "offline cache is the real data store, not a bolt-on").
- `src/firebaseConfig.js` — the public Firebase project config object (not secret, safe to commit — see the comment in the file).
- `src/lib/authReady.js` — `waitForInitialAuthState()`, the bounded (4s) timeout around Firebase Auth's own init calls (spec.md §1a's cold-start-stall mitigation). Any future code that needs "is there a signed-in user yet" at startup should use this rather than reading `auth.currentUser` directly or assuming `onAuthStateChanged` fires promptly.
- `src/sw.js` — hand-written service worker source, built via `vite-plugin-pwa`'s `injectManifest` strategy (**not** `generateSW`, which is the default and does *not* give network-first navigation — a real footgun already hit once during Phase 0: the option is `strategies` (plural), and a `strategy` typo silently falls back to `generateSW` with no error). Implements: precache-and-route from the real build manifest, and a `NavigationRoute` wrapped in `NetworkFirst` (2.5s timeout, `app-shell` cache) so navigation never serves a stale cached shell while online (spec.md §1a).
- `src/index.css` — Tailwind import, the semantic color tokens from spec.md §1b.4 (as CSS custom properties, light + `prefers-color-scheme: dark`; manual override switch not built yet — lands with the Settings screen), self-hosted Inter/JetBrains Mono via `@fontsource/*` (not a Google Fonts CDN link — offline-first means no runtime dependency on a third-party host for something as basic as page text), and the `overscroll-behavior: none` / `touch-action: pan-y` fix from spec.md §1.
- `public/icons/` — placeholder PWA icons (flat-color circle mark, programmatically generated, not a real design) — swap these out whenever real icon design happens; nothing depends on their current appearance.
- `firebase.json` / `.firebaserc` / `firestore.rules` / `firestore.indexes.json` — Firestore-only Firebase config (no `hosting` key — GitHub Pages serves the app, not Firebase Hosting, per spec.md §1b.1). `firestore.rules` is live with the real single-admin-UID rule (§1a/§1b.1) — Markus's actual Google account UID, not a placeholder — confirmed working via real signed-in usage throughout Phase 1a/1b (the 2026-09-22 import, and all of Konten's real editing since).

### `migration/` — one-off 2025 + 2026 import from the Gsheets (PLAN.md Phase 1a)

Not part of the app bundle. Python scripts that turn Markus's yearly "Geld 2025" / "Geld 2026" Google Sheets into Firestore-shaped JSON, each with built-in checks against the sheet's own totals that fail loudly on any mismatch.

- `migration/seed/` — **committed**, non-personal static data transcribed from spec.md: `accounts.json` (§2.2 — the seven `receivable` accounts carry `reportingGroup: "Außenstände"`, revised Sept 2026), `categories.json` (§2.4), `tags-allocation.json` (the 7 allocation tags, §2.5). **A change here needs re-running `ImportScreen` for that file to actually reach Firestore** — editing the seed JSON alone doesn't touch already-imported data.
- `migration/transform-transactions.py [year]` — `Konten` tab → that year's transactions; for 2025 also the one-time Jahresabschluß opening balances. Later years skip their sheet's own opening rows and are checked against the full history (Jahresabschluß + every year so far), so the later sheet's header must come out of the app's own carry-over; known carry-over differences are either booked (`CARRYOVER_CORRECTIONS`) or explained by an earlier-year `CORRECTIONS` entry. Core rule, verified against the sheet: every row changes only its own Konto (`Σ Teilwert per Konto` is the sheet's header formula; `Wert` never counts); transfers appear as two rows and are paired globally, unpaired rows stay single-sided. Confirmed data-entry typos live in its `CORRECTIONS` table. Checks: all 18 account balances, all 7 allocation-tag totals, all 59 claims (open/settled, per receivable account) against the sheet.
- `migration/transform-budgets.py [year]` — `Verlauf` tab → Plan0 + Plan1 budgets and their breakdown-line grouping tags (Prog is not imported — computed live). Checks: group totals per month against the Verlauf summary rows, savings actuals per month against the Prog rows.
- `migration/out/` — **gitignored**, generated output (real personal data). **This repo is public (GitHub Pages) — nothing personal may ever be committed.** The generated files will reach Firestore via the app's one-time import screen (file picker, not bundled into the public app).

To regenerate: export each year's sheet from Markus's Google Drive as `.xlsx` (the Drive connector's download with the xlsx export type keeps every tab — CSV export only gives the first tab), save it at the path in each script's `SRC` constant, then run in this order: `transform-transactions.py 2025`, `transform-transactions.py 2026` (needs the 2025 output), then `transform-budgets.py 2025` and `2026` (each reads its year's transactions for the savings check). Needs `openpyxl`.

## Screen-to-component map

- `src/Konten.jsx` — the main ledger grid (PLAN.md Phase 1a). Loads `accounts`/`categories`/`transactions` live via `onSnapshot` (all-time, not year-scoped — `balance()` needs the full history, §2.1/§2.3/§2.8), computes a year list from the loaded transactions' own dates, and renders a pinned per-`reportingGroup` balance panel (Barkonten/Sparkonten/Geldanlage/Außenstände, via `jahresende()`) above an AG Grid (`ag-grid-community`/`ag-grid-react`, Theming API — `themeQuartz`, Community-tier `AllCommunityModule`) listing the selected year's transactions. **Confirmed against the real 2025 import: every account's Jahresende matches the Gsheet's own closing balance** — Phase 1a's actual testable deliverable (PLAN.md).
  - **The grid follows system dark mode now, like the rest of the app** — `src/lib/gridColorScheme.js`'s `syncAgGridColorScheme()` (called once, at module load). `themeQuartz` ships light/dark params out of the box (its `colorSchemeVariable` part), but they're gated behind a `data-ag-theme-mode` attribute on `<html>`/`<body>` that nothing was ever setting, so the grid always rendered in its light default regardless of the app shell correctly following `prefers-color-scheme` via CSS (Markus: illegible in dark mode). Verified visually with a standalone Playwright harness (not just read from source) before shipping — AG Grid's own dark palette, not tied to this app's own CSS tokens, so it won't match exactly, but reads correctly and legibly. Reusable as-is for a future AG Grid screen (Verlauf, §1b.3) — idempotent if called again.
  - **Column order matches spec.md §3a exactly:** Datum → Konto → Empfänger → Betrag → Kategorie → Unterkategorie → Details → Tags (plus an unlabeled, pinned-right delete column, not part of the spec'd order). Konto is one merged column showing the primary account with an arrow to the second one for a transfer (not Konto1/Konto2 — see spec.md §3a's note on why). Kategorie (the parent group) is derived from Unterkategorie's `parentCategoryId`, never stored separately. `signedFor(tx, accountId)` — the same magnitude-by-position rule `balance()` uses — powers the Betrag column, the Konto arrow's direction, and the account filter below.
  - **Account filter** (a `<select>` grouped by reportingGroup via `<optgroup>`, plus clicking an account in the pinned panel): matches every transaction where the chosen account is either side, and re-displays Konto/Betrag from that account's own perspective (the other account, and the amount signed relative to it). The pinned panel's own account buttons have their own roving keyboard navigation (below), richer than the plain `<select>`.
  - **Manual entry is fully built**: "+ Neue Buchung" creates a blank row below the selected one (pre-filled with the active account filter, if any) and cell-focuses its Datum cell without starting to edit it; every column is editable in place via one `setDoc` full-overwrite per commit (`persistTx`). Deleting is a pinned trashcan (or the keyboard Delete key) with a two-click arm/confirm — the armed row tints pale red (`--color-alert-tint`) and Escape discharges it. This is a real hard `deleteDoc`, not spec.md §2.9a's planned soft-delete-with-recovery-window (Phase 1b) — Firestore's PITR (7-day window, since Phase 0) is the actual safety net until then.
  - **Split transactions (§3a's auto-remainder mechanism, Phase 1b) are built.** AG Grid Community has no master/detail row support (that's Enterprise-only) — `displayRows` (a `useMemo` flat-mapping `rows`) is the Community-tier equivalent: an expanded split transaction's `lines[]` get interleaved right after their parent as synthetic rows (`{ id, __isLine: true, __parent, __lineIndex }`, `__parent` a live reference into `rows`), and every column def branches on `p.data.__isLine` to render/edit differently for a line row vs. its parent. A pinned-left "split" column (`colId: 'split'`) handles expand/add: ✚ on an unsplit parent starts the first split and auto-expands; a chevron toggles `expandedIds` once split (`>1` lines); the *last* line (the live remainder) also gets ✚ to split further. Appending a blank line is the same operation whether it's the first split or splitting an existing remainder further — no special-casing needed, since the previously-last line simply becomes directly editable and the newly-appended one becomes the new remainder. **Removing a line goes through the trashcan column instead** (Markus) — it arms/confirms/red-tints exactly like deleting a whole transaction (`handleDeleteClick` now takes the row itself and branches: `removeLine` for a line row, `deleteDoc` for a parent), not a separate instant-remove affordance; `confirmDeleteId` doesn't care whether the id it holds belongs to a parent or a line row.
    - **Ctrl/Cmd+T ("Teilen") triggers the same add/split-further action as the ✚ button**, for whichever transaction the cursor currently sits on (its parent row or any of its own line rows) — reads the focused cell's row via `api.getFocusedCell()`/`getDisplayedRowAtIndex()`, resolves `__isLine ? __parent : row`, then calls `addSplitLine` exactly like the button would. Both the button and the shortcut land the cursor specifically on line index 0's own Betrag cell afterward (`pendingFocusColRef = 'betrag'`, `pendingFocusLineIndexRef = 0`, always the *first* line literally, even when splitting further deep into an already-multi-line split) — the natural next step either way is typing how much that first piece is. Betrag has an explicit `colId: 'betrag'` now so this can target it reliably.
      - **Was Ctrl+Enter originally** — registered on `window` with capture phase and `stopPropagation()` to win a real race against AG Grid's own native keydown listener on the row container (`RowContainerEventsFeature`, confirmed in its bundled source; same underlying lesson as `Listbox.jsx`'s Enter fix, Session 21: a page-level handler can't out-run a closer native one without running first). That fix was necessary but not sufficient — Markus reported it still didn't fire, most likely because Enter itself is also one of the most universally browser/OS-reserved key combinations there is on some platforms (iPadOS's own external-keyboard handling included), meaning the browser/OS can swallow the keypress before it's ever dispatched to the page's JavaScript at all — a layer no in-page fix can reach. Reassigned to Ctrl+T instead (Session 31) — the capture-phase/stopPropagation fix is kept regardless (still correct, still needed for the in-page AG Grid race, harmless either way), even though T isn't a key AG Grid's own core claims. **T itself is a real gamble in the same category** — it's *the* nearly-universal "open new tab" browser shortcut, arguably reserved even more aggressively than Enter — so if it silently fails too, that's the same browser/OS-level obstacle, not this code.
    - **A line row's synthetic id bakes in its parent's current line *count*, not just its own index** (`${tx.id}::line::${i}::${tx.lines.length}`) — a line has no stable id of its own in the schema (§2.6). Index-alone ids meant removing a non-last line shifted every later line's index, so a surviving line inherited a *different* line's old id under AG Grid's own id-based reconciliation, which can't tell "this row moved" from "this id now holds different content" — a stale leftover row after deleting a non-last line (Markus). Baking the count in forces a full rebuild of that transaction's line rows on any add/remove, while keeping ids (and smooth updates) stable across a pure value edit, which doesn't change the count.
    - **The cursor/selection stays on the exact split line just edited**, not the parent (Markus) — `handleCellValueChanged` carries the edited line's index through `pendingFocusLineIndexRef`, and the settle effect looks that line's row up by `__parent` + `__lineIndex` rather than reconstructing its (now count-dependent) synthetic id, falling back to the parent's own row if that line no longer exists by the time it runs.
    - **The invariant (parent `amountCents` === Σ `lines[].amountCents`) is enforced on every save**, not checked after the fact: `persistTx` recomputes the *last* line's `amountCents` from `src/lib/split.js`'s `withRemainder()` whenever `lines.length > 1` — every other line is directly stored as typed. The parent's own amount becomes non-editable once split (a fixed total that splitting only ever redistributes, never changes); a single line (≤1) keeps the older "parent is authoritative, mirrors down into the line" behavior instead.
    - Each line has its own `note` (shown "↳ `note`" in the Empfänger column — display-only prefix, the raw editable value has none), its own `amountCents` (editable except on the last/remainder line), `categoryId` (via the same `CategoryEditor` popup as the parent, parameterized per-row through a `cellEditorParams` *function* rather than a static object, and a new `initialCategoryId` prop on `CategoryEditor` replacing its old `data.lines[0]`-derived default so it works identically for a line or a parent), and `tags`.
    - **Known gap, narrowed, not fully closed:** adding/splitting-further is now Ctrl+T, and removing a line is the Delete key (same as a whole transaction) — both fully keyboard-reachable. The expand/collapse chevron itself is still mouse/tap-only; AG Grid's own cell focus (reachable via arrow keys) is a different thing from real DOM focus on the button inside that cell, so Enter on a keyboard-focused split-column cell still doesn't toggle it. Worth a dedicated pass if real usage shows that's still missed.
    - **Every sortable column has a custom `comparator`, not just Datum** — `glueToParent(getValue)` (module-level helper), given a function that computes a column's "parent-level" value, compares *every* row by its own parent's value; a line row and its parent always tie under this rule, and JS's stable sort preserves `displayRows`' own build order for the tie, keeping a transaction's lines adjacent to it regardless of which column is actually driving the sort. Session 27's first pass only wired this up for Datum (the always-active default sort) — Markus then caught that sorting by any *other* column still scattered an expanded transaction's lines back to the top, since only Datum's comparator existed yet. Each column's "parent-level" value is a small extracted function (`kontoValue`, `betragValue`, `kategorieValue`, `unterkategorieValue`, `tagsValue`, plus inline ones for Datum/Empfänger/Details) shared between its `valueGetter` (parent-row display) and its `comparator`, so the two can't quietly drift apart. Betrag glues a line to its parent's *total* for sorting too, not the line's own distinct amount — sorting the whole grid by every individual split line's own amount wouldn't be meaningful either way.
    - Line rows get a distinct subtle background (`--color-line-row-tint`, `src/index.css`) via `getRowStyle`, so they read as visually separate from ordinary transaction rows.
    - The split column's own button clicks (add/remove/split-further) route through the same `pendingFocusIdRef`/`rows`-settle mechanism `handleCellValueChanged` already uses, rather than leaving AG Grid's own selection state to drift — these are button clicks, not cell edits, so without this nothing told the grid which row to re-select once each action's Firestore round-trip landed, which showed up as a stale blue tint on an unrelated row (Markus, screenshot).
    - **A second, independent way to land the cursor back on the grid — `focusGridMidViewport()`, used by the pinned panel's own Ctrl+K/Escape/Enter flow (below) — has its own immediate `setTimeout(0)`, not gated on `rows` settling at all** (it often has nothing to wait for; a filter change doesn't necessarily change the row *set*). Two genuinely independent deferred callbacks that each call both `setFocusedCell` and `setSelected` can interleave — an edit made just before Ctrl+K/arrow/Enter can still have its own settle effect pending when this one fires — and since neither pair of calls is atomic against the other's, one callback's `setFocusedCell` and the other's `setSelected` can each "win" separately, splitting the cell-focus rectangle and the blue selection tint across two different rows (Markus, screenshot). **Note: this race was a plausible reading of Markus's screenshot but turned out *not* to be what he was seeing** — the tint that stayed on "the middle visible row" while scrolling was AG Grid's own row-hover highlight sticking to a touchscreen's parked pointer, now turned off via `suppressRowHoverHighlight`. The guard below is kept anyway as a harmless safeguard against the real (if unobserved) interleaving. Guarded with a shared monotonic counter (`focusClaimRef`) bumped by every claimant (`claimPendingFocus(id, colId, lineIndex)`, used everywhere the old three-line `pendingFocusIdRef`/`pendingFocusColRef`/`pendingFocusLineIndexRef` assignment used to appear directly, plus `focusGridMidViewport`'s own claim) — each deferred callback checks the counter is still its own claim right before applying anything, so a superseded claim silently no-ops instead of partially overwriting a newer one; `focusGridMidViewport` also clears `pendingFocusIdRef` outright so a same-id edit-settle that hasn't fired yet can't spuriously re-claim later off some unrelated future `rows` change.
  - **Konto and Kategorie/Unterkategorie are custom popup editors, keyboard-chainable end to end:**
    - `src/KontoEditor.jsx` — two account pickers (Von/Nach), resolving spec.md §3a's open question of how you edit a merged Konto cell. Both columns (Kategorie and Unterkategorie) open `src/CategoryEditor.jsx`'s cascading Kategorie→Unterkategorie pair, since Kategorie has no stored value of its own.
    - Both use `src/Listbox.jsx` — a custom-rendered dropdown, not a native `<select>`. A native select inside these popups wasn't opening at all on tap on Markus's device (most likely a stacking/rendering conflict between a native form control's own popup and AG Grid's own popup positioning, which applies a CSS transform) — building it ourselves sidesteps that instead of chasing the exact cause. Focusing a Listbox opens it immediately; Enter on a highlighted option commits it and (via each editor's `onEnter` wiring) either advances to the next Listbox or applies and closes, matching the flow Markus described: cursor on the cell → Enter → arrow through the first list → Enter → arrow through the dependent list → Enter → applied, back to normal grid navigation.
    - Übernehmen/Abbrechen buttons remain for mouse/touch use — the Enter chain is the keyboard equivalent of the same `apply()` call, not a separate path. `apply()` takes an optional override argument for whichever value was *just* committed via Enter, since a Listbox's `onEnter` fires synchronously before React re-renders the state `onChange` just set — reading plain state at that exact instant would still see the previous value.
    - Übernehmen writes directly via `cellEditorParams.onApply` (`applyKontoDirect`/`applyCategoryDirect` in `Konten.jsx`, persisting via the shared `persistTx`) and closes with `api.stopEditing(true)` (cancel — already persisted), rather than going through AG Grid's own `getValue()`/`stopEditing()` commit pipeline. That pipeline's own popup-dismiss listener only ever attaches when the popup is `modal` (`stopEditingWhenCellsLoseFocus`, which this grid never sets) — confirmed never the actual mechanism at play, and confirmed unreliable for a different, still-unidentified reason, so nothing here depends on it working.
    - Editing works the same regardless of the account filter — Konto's editor always edits the real `fromAccountId`/`toAccountId` directly, and Betrag's `valueSetter` uses the same "reference account" its `valueGetter` already displays.
    - A parent row's Kategorie/Unterkategorie stays editable only while it has ≤1 line — once split, per-line category editing happens on the expanded line rows instead (above).
  - **Tags — the real mechanism (spec.md §2.5), not the earlier comma-separated-text placeholder.** New `tags` Firestore collection, loaded the same way `accounts`/`categories` already were (`onSnapshot`, `tagById` lookup memo). `src/TagEditor.jsx` is a new popup cell editor, same family as `KontoEditor`/`CategoryEditor` — a multi-select autocomplete: type to filter existing (non-archived) tags, Enter/click a suggestion to add it as a removable chip, "Tag '…' erstellen" when nothing matches. Same direct-write-then-`stopEditing(true)` pattern as Konto/Category's own Übernehmen (`applyTagsDirect`/`applyTagsToLine` in `Konten.jsx`), with a fallback `valueSetter` for however else an edit might end (blur) — unlike Kategorie's, this one has no truthiness guard, since an empty tag list is a fully valid commit. `cellEditorParams` is a per-row function exactly like Kategorie/Unterkategorie's, branching on `__isLine` the same way.
    - **claim-category sequencing (spec.md §2.5) is enforced in the suggestion list itself**: a `groupingType: "claim-category"` tag (Meal/Taxi/…) is filtered out of the autocomplete entirely unless the line already carries a tag with `groupingType: "claim"` — not a separate mode, just a filter condition alongside "not archived" and "not already selected."
    - **New tags are always `class: "grouping"`, never `allocation`** (spec: allocation tags are fixed/pre-seeded, a deliberate Settings-area action, never created while entering a transaction) — `createTag()` in `Konten.jsx` writes a new doc with a slugified id (collision-suffixed if needed) and `groupingType: null`.
    - **`createTag()` parses a colon as parent:child** (Markus, real-usage feedback, Sept 25) — "Schottland:Fähre" reuses an existing top-level "Schottland" tag by name (case-insensitive) or creates one, then creates/returns a real child tag under it (`parentTag` set, spec.md §2.5's hierarchy). The id actually applied to the line is always the child's, matching spec's own breakdown-rollup note that an untagged child contributes nothing to its parent's rollup. `src/lib/tagStyle.js`'s new `qualifiedTagName(tag, tagById)` renders a child as "Schottland: Fähre" everywhere a tag name is shown (TagEditor's chips/suggestions, the Tags column, the sort comparator) — a bare "Fähre" would be ambiguous outside Verlauf's own already-grouped breakdown block (unlike that block, §2.7's own display-convenience note doesn't apply here).
    - **Suggestions are usage-derived for grouping tags** (Markus, real-usage feedback, Sept 25 — the original build offered every seeded/created grouping tag regardless of whether it was ever actually used, and separately never offered a *pre-mechanism free-text* tag like an informal loan's own label at all, since those were never real tag documents to begin with). `usedTagValues` (`Konten.jsx`, a `Set` built from every value in every line's `tags[]` across all loaded transactions, any year) drives two things in `TagEditor`: a grouping tag is only ever suggested if it's currently used somewhere, **whether browsing or typing** (revised same day — an earlier pass only applied this filter to the empty-input browse case, which Markus caught as still cluttered while searching); and any value in `usedTagValues` that isn't a real tag id at all becomes a selectable "legacy" suggestion in its own right (not just a chip once it's already on the current line) — reusing Markus's existing informal-loan/trip labels without silently forking near-duplicates. The one exception to the usage gate: a real tag whose *qualified name* exactly matches the typed text is still offered even if unused, so a real-but-currently-unused tag never becomes a true dead end (can't create a duplicate of it, and otherwise couldn't reach it at all). Allocation tags are exempt from the usage filter entirely (always structurally relevant). `canCreate`'s "does this already exist" check covers both real tags and legacy values, so typing an exact existing legacy string's name no longer also offers a redundant "create" option next to the real match (a bug caught by the harness re-run below).
    - **Tag creation offers a type** (Markus asked directly: "how can i create a new travel tag or statement tag etc?" — resolves the open question logged the previous session). Instead of one "Tag '…' erstellen" row, up to five — one per groupingType (Reise/Projekt, Abrechnung, Anspruch, Anspruchsart — the last gated by the same claim-tag-already-present sequencing rule as everywhere else — plus Unbestimmt) — each independently navigable/selectable via the same Arrow/Enter mechanism as ordinary suggestions. `CREATE_TYPES` (`TagEditor.jsx`) lists Unbestimmt *first* deliberately: a plain Enter with nothing arrowed to still creates unspecified, exactly the old default behavior, so this is additive, not a workflow change for anyone not using it. `onCreateTag`/`createTag`/`createPlainTag` (`Konten.jsx`) all now take the chosen `groupingType` through to the actual `setDoc`; for a "Schottland:Fähre"-style parent:child creation, the chosen type applies to the child (the one being categorized in context), a newly-implied parent still always starts unspecified.
    - **Selecting a suggestion (or a create-type row) applies and closes the popup immediately** (Markus: "rarely ever will i select two tags in one go") — `selectSuggestion()` computes the new tag id directly and calls `onApply`/`api.stopEditing(true)` itself rather than routing through `setSelectedIds` first (that state update wouldn't be visible on the same call anyway, and the popup is closing regardless). Removing a chip via its own `×` deliberately still doesn't auto-close — only *adding* a tag does — so fixing a mis-tagged line (remove the wrong one, pick the right one) stays a single visit to the popup.
    - **The 5 most-recently-used tags sit above a separator at the top of the empty-input browse list** (Markus). `recentTagValues` (`Konten.jsx`, a plain array — every used value, real tag id or legacy string alike, ordered by its own most recent transaction date) — `TagEditor` takes the first 5 of these that are still real suggestion candidates (already filtered for archived/selected/claim-category-sequencing) and lists them first, with an `<hr>` after, only while the input is empty (typing a search drops back to plain relevance-ordered matches — a "recent" section didn't make sense mixed into active search results).
    - **Color-coding** (`src/lib/tagStyle.js`'s `tagColorVar(tag)`) maps class/groupingType to the CSS tokens added to `index.css` for this — allocation reuses `--color-savings` (already purple, §1b.4), the four grouping types get their own new tokens (`--color-tag-project` teal, `--color-tag-statement` slate, `--color-tag-claim` indigo, `--color-tag-claim-category` rose). **Revised (Markus, real-usage feedback, Sept 25): `groupingType: null` and an unresolved legacy string now both return `null` (no color) rather than the statement-gray token** — a freshly-created "unspecified" tag rendering as a solid gray fill looked inconsistent right next to an old free-text tag's plain outline, so both now get the exact same plain dashed-border/no-fill treatment; only a tag with a genuinely determined type gets a colored fill. Chips render via `color-mix(in srgb, var(...) 15%, transparent)` for the background, the plain var for the text, when a color exists — same helper used by TagEditor's own chips, the Tags column's read-only `cellRenderer`, and now the pinned panel (below).
    - **Backward compatibility with pre-mechanism free-text tags is deliberately conservative, not auto-migrating:** every tag typed before Sept 24 is a raw string with no real tag document behind it. `tagById` lookups fall through to the plain string everywhere, styled per the point above — they're not silently promoted into new tag documents (would risk quietly multiplying the `tags` collection with typo-derived near-duplicates unsupervised), but Sept 25's usage-derived suggestions (above) do make them properly *reusable* now, which was the actual gap Markus hit in practice.
    - **`slugify()` (`TagEditor.jsx`) transliterates German umlauts/ß before stripping other non-alphanumeric characters** — caught by the harness re-run below: "Fähre" produced the id `f-hre` before this (the diaeresis just vanished), now `faehre`.
    - **Verified via a standalone Playwright harness** (scratchpad, not part of the repo — same approach as Session 25's AG Grid dark-mode check), re-run for every fix in this pass, not just the original build: usage-derived suggestions (an unused tag hidden on empty browse, reachable by typing its name), a legacy free-text value surfacing as a real suggestion, the `canCreate` fix, the slugify fix, and "Schottland:Fähre" correctly reusing an existing parent and creating a real child — checked against real rendered/interactive output with fake data before Markus's own test, not just reasoned from source.
  - **Allocation-tag balances surface in the pinned panel itself, as full filter buttons — not a read-only display** (`src/lib/tagBalance.js`'s `tagBalance()`/`tagJahresende()`, tested in `tagBalance.test.js` — same shape and same "no Firestore access, pure function" discipline as `balance.js`), per spec.md §3a's own "Live consistency checks... should surface here" note and Markus's explicit request (Sept 25) to actually see them, not just trust the invariant holds invisibly. Summed per *line* (a tag lives on `lines[]`, §2.6), directional sign generalizing `balance()`'s own account-position rule to a tag's full `reconciliationTargetAccountIds` set: `+` when the parent transaction's `toAccountId` is one of the tag's targets, `−` when `fromAccountId` is, both checked independently (not either/or) so a transfer *between* two of a tag's own target accounts (e.g. Aktien → Crypto, both inside Anlage Familie's combined pool) nets to zero rather than double-counting. **Uses the line's own signed `amountCents` directly, not `Math.abs()` first** (fixed same day — Markus: Anlage Familie off by a real amount) — unlike `balance()`'s account-position rule, where a transfer's `amountCents` is always already a stored positive magnitude (§2.6) so `Math.abs()` is a no-op there, a *line's* own sign can genuinely differ from its parent's (§2.6's salary-split example: positive Gehalt / negative Steuern), and forcing `Math.abs()` first silently flipped a negative line's real contribution to positive. Exactly mirrors `migration/transform-transactions.py`'s own `allocation_tag_delta()` — the reference implementation already checked against the real Gsheet totals during the original migration (`verify_tag_sums()`), which never took `abs()` either, for the same reason. `panel`'s `useMemo` (`Konten.jsx`) computes each reportingGroup's `tagItems` — every allocation tag whose targets intersect that group's own account ids — appended into the **same** account `<ul>` as real filter buttons, not a separate read-only list (revised same day: Markus explicitly wanted them "fully part of the cycling with arrow buttons," not just visible). A tag targeting a combined multi-account pool (Anlage Familie/Sophia) shows once under that group, not once per account.
    - **`accountFilter` (the shared state, despite its name) now holds either a real account id or an allocation tag id.** `filteredAccountId` (a derived value, `accountById[accountFilter] ? accountFilter : null`) is what every *account-specific* consumer reads instead when it only makes sense for a single reference account — Konto's re-signed arrow display, Betrag's re-signed amount, `addRow`'s account prefill, the plain `<select>` dropdown's `value` (accounts-only, so a tag filter shows it as "Alle Konten" rather than nothing selected). It's deliberately `null` whenever the filter is actually a tag: a tag can span several target accounts at once (Anlage Familie), so there's no single meaningful "the other side" to re-sign against — a tag-filtered row just shows its own natural, unfiltered Konto arrow and amount sign. `rows`' own filter predicate, by contrast, reads `accountFilter` directly and branches on `filteredAccountId` itself to decide *how* to match (by `fromAccountId`/`toAccountId` for an account, by `lines[].tags` containment for a tag).
    - **The account and tag buttons share one `<ul>` per reportingGroup, tag rows last**, so the existing keyboard cycling (`closest('ul').querySelectorAll('button')` for Up/Down) sweeps through both together for free — no separate handling needed. The shared DOM marker was renamed `data-filter-id` (was `data-account-id`), read by both the keyboard handler and Ctrl+K's own "return to the active filter's button" lookup. A tag button's color comes from `tagColorVar` (a plain `style`, since Tailwind can't do arbitrary dynamic CSS-var text colors); active-state highlighting is `font-semibold` for a tag (keeping its own color) vs. the existing computed-blue swap for an account.
  - **Datum is a plain text cell, not a picker of any kind** (Markus specifically didn't want one) — `parseFlexibleDate()` accepts the stored `"YYYY-MM-DD"` as-is, or European shorthand (day first, always): `D.M`/`D/M` with the year taken from the app's own year selector, or `D.M.YYYY`/`D/M/YYYY` with an explicit year (2-digit read as 20XX). Goes through the same default AG Grid text editor + `valueSetter` pipeline `displayLabel`/`detail` already use successfully — no custom editor component, since the popup-based approach tried first for this had its own reliability problems (see above) that a plain text field doesn't have.
  - **Columns are fixed** — `defaultColDef={{ suppressMovable: true }}` blocks drag-reordering; Community edition never shipped a hide-columns tool panel (an Enterprise module, never registered).
  - **`singleClickEdit={true}`** on the grid overall — AG Grid's default is double-click-to-edit.
  - **Row selection (the blue tint) follows keyboard cell focus, not just clicks** (`onCellFocused` calls `setSelected` on whichever row the focus lands on) — also means "+ Neue Buchung"'s insert-below-selected-row follows wherever the keyboard cursor is.
  - **Three global shortcuts:** Ctrl/Cmd+`'+'` **or Ctrl/Cmd+N** triggers "+ Neue Buchung" (noted: `'+'` is also the browser's own zoom-in shortcut everywhere, and N its own "new window" shortcut nearly everywhere — browsers commonly refuse to let a page override either, so neither may be fully reliable on every platform; N added alongside `'+'`, not replacing it, per Markus). Ctrl/Cmd+K always jumps into the pinned panel's account boxes (never the plain `<select>`) — the active filter's own button if one is set, otherwise the first account overall. Ctrl/Cmd+T ("Teilen") starts/continues a split on whichever transaction the cursor is on (the split column's own ✚, above).
  - **The pinned panel's account buttons have their own roving keyboard navigation, richer than the `<select>` above:** ArrowUp/Down moves within one reportingGroup's `<ul>` and applies the filter live as it moves (`data-account-id` on each button, `data-group` on each panel `<div>`); ArrowLeft/Right jumps to the first account of the adjacent group box in fixed order (Barkonten/Sparkonten/Geldanlage/Außenstände) via DOM sibling traversal. Escape resets to "Alle Konten" and hands focus back to the grid; Enter keeps the highlighted filter and also hands focus back to the grid (`focusGridMidViewport()`, shared by both) — landing on the Datum cell of whichever row is roughly mid-viewport (`getFirstDisplayedRowIndex`/`getLastDisplayedRowIndex`, deferred a tick so a filter change has actually re-rendered the row set first). Ctrl+K, arrow, Enter, Ctrl+K again is a closed loop back to the same button.
  - **Still not built:** the real tag-autocomplete mechanism, the quick-filter text box, per-field column filters, date-range presets, saved filters (§3a), and the auto-suggested transfer-leg matching (also §3a — creating one side of a transfer today just makes a single-sided row; nothing suggests pairing it with the other leg yet).
  - **Phone-specific condensed layout (§1b.7/§3a's compact card view) isn't built at all** — Konten today is the same grid+panel at every width, just reflowing. **Fixed, though (Sept 2026):** the page itself couldn't scroll on a narrow screen — `App.jsx`'s `main` was `overflow-hidden`, which worked while the pinned panel was short (tablet width, 3-4 columns) but trapped it unreachably once it stacked to four tall blocks on phone width. `main` is `overflow-y-auto` now, and the grid has a fixed height (`h-[70vh]`) instead of `flex-1`/`min-h-0` (which depended on a bounded parent height that no longer holds on every screen size).
  - **Known gap to watch:** `ag-grid-community`'s `AllCommunityModule` pulled the precached bundle from ~850 KB to ~2 MB (still under `vite-plugin-pwa`'s 6 MB cap, but worth revisiting — importing only the specific feature modules Konten actually uses, instead of the "all community features" bundle, would likely cut this significantly).
- `src/ImportScreen.jsx` — **temporary, Phase 1a's one-off data loader**, not a routed screen (no router yet). Lets Markus pick the JSON files `migration/`'s scripts generated (sent to him directly, never committed — see `migration/`'s own section above) and batch-writes them into Firestore via `writeBatch`, routing by filename into `accounts`/`categories`/`tags`/`transactions`/`budgets`. ## Shared/pure calculation functions

- **`balance(accountId, asOfDate, transactions)`** — `src/lib/balance.js`, tested in `src/lib/balance.test.js` (`npm test`, run in CI before every deploy — see `.github/workflows/deploy.yml`). All-time running balance per spec.md §2.1/§2.6/§2.8: magnitude signed by the account's own position (`fromAccountId`/`toAccountId`), never the stored field's raw sign applied to both sides. Also exports `jahresanfang()`/`jahresende()`, the computed-lookup helpers from §2.1/§2.3.
- **`tagBalance(tagId, asOfDate, transactions, tags)`** — `src/lib/tagBalance.js`, tested in `src/lib/tagBalance.test.js`. The same computation, generalized to an allocation tag's own `reconciliationTargetAccountIds` set instead of one account id, and summed per *line* rather than per transaction (§2.6 — a tag lives on `lines[]`). Also exports `tagJahresende()`. Powers the pinned panel's allocation-tag rows (Konten.jsx).
  - **The committed test suite uses synthetic fixtures, not Markus's real 2025 figures** — a deliberate deviation from PLAN.md Phase 1a's original wording ("tested against 2025's real migrated figures"), forced by the standing privacy rule (no real financial data in this public repo, ever). The equivalent real-data validation already happens, just not as a committed unit test: `migration/transform-transactions.py`'s `verify_account_sums()` implements this exact same per-account-position sign rule and checks it against the real Gsheet totals for every account, every year (CODEMAP.md's `migration/` section above) — and `Konten.jsx`'s pinned balance panel is itself a second, live confirmation of the same thing against real data, just never captured as a repo-committed test.
- **`withRemainder(amountCents, lines)`** — `src/lib/split.js`, tested in `src/lib/split.test.js` (PLAN.md Phase 1b's own called-out test-suite addition: "the split-transaction invariant"). Given a fixed parent total and a `lines` array with length > 1, returns a new array with every line but the last unchanged and the last recomputed as whatever's left — the pure core of `Konten.jsx`'s `persistTx`, which is the only caller and only invokes it once `lines.length > 1` (a ≤1-line transaction mirrors the parent's amount down into the line instead, a different, simpler rule that stays inline in `persistTx` rather than being extracted).

## Known duplication or drift to watch

- **The year selector lives inside `Konten.jsx` itself, not the app shell header** — spec.md §1b.2a specifies "a single year selector lives in the app shell header (not per-screen), and drives every year-scoped view." Right now there's only one real screen, so building it inside `Konten.jsx` (its own `years`/`setYear` state and the row of year buttons in its own JSX) hasn't caused any actual duplication yet — but it's a real divergence from the spec'd architecture, not just an implementation detail, and it's exactly the kind of thing that needs deliberate attention (not a copy-paste) when Verlauf (Phase 3, which also needs a year selector per spec.md §1b.2a) gets built alongside the real nav shell. Move it up into `App.jsx`'s header then, rather than adding a second independent one inside Verlauf.
